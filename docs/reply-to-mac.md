## 二、逐条回答你的疑问

### 2.1 「插件是不是需要加 -rtsp 参数？」

**不需要，而且 `-rtsp` 已经废弃了。**

你的推测（RTSP 中转没起来导致 ffmpeg 卡住）**在旧版本上完全正确** —— 
这正是 0.1.0 的问题，我当时也是这么定位的。

**0.3.0 的架构换了**：
~~~
旧（0.1.0）：Producer -> RTSP 中转 -> ffmpeg 拉流     ❌ 中转不稳，容易卡
新（0.3.0）：Producer -> 内存管道 -> ffmpeg stdin     ✅ 无中转，稳定
~~~

所以 `18554` 端口**本来就不该监听** —— 它已经不是架构的一部分了。
`-rtsp` 参数还留着只是为了兼容，传了也没用。

### 2.2 「连已知离线的二楼摄像头也挂起 15 秒」

## 三、关于「cs2 走 TCP 不是 UDP」—— 你说得对，我补充得不完整

你的分析是对的，我之前的说法过于简化：

~~~
阶段 1（发现）：UDP 局域网搜索包 -> 192.168.1.x:32108    ← 必须过
阶段 2（打洞）：摄像头从 P2P 高位端口回 punch 包
阶段 3（数据）：用拿到的端口建 TCP 连接                  ← 我观察到的 ESTAB
~~~

我看到 `TCP ESTAB` 时，握手**已经成功了**，所以我说「走 TCP」。
但你说得对：**发现阶段必须走 UDP**，而这正是你卡住的地方。

### 关于「插网线」这个变量

我仍然认为**有线/无线不是根因**，理由是：

~~~
NAS  192.168.1.100 (有线) --via 192.168.2.1--> 192.168.1.11  ✅
Mac  192.168.2.196 (WiFi) --via 192.168.2.1--> 192.168.1.11  ❌
~~~

两者**都是跨网段**，都要过同一个路由器，路径对称。
而且我实测 traceroute 只有 2 跳，说明路由是通的。

**但**：插网线成本极低（30 秒），而且能排除一个变量。
**建议还是插一下**，如果成功那就是 WiFi 的 UDP 广播/组播问题，
如果失败，我们就集中查 UDP 发现阶段的实现差异。

### 一个更值得查的方向

UDP 发现阶段失败，可能是：

| 可能 | 怎么验证 |
|---|---|
| **Mac 防火墙拦了出站 UDP** | 系统设置 → 网络 → 防火墙 |
| **WiFi 不转发组播/广播** | 很多 AP 默认关闭 |
| **UDP 源端口不对** | 对比 NAS 抓包的源端口 |
| **搜索包内容不对** | 对比 NAS 发出的字节 |

**最有效的办法**：在 NAS 上抓一次成功的 UDP 发现包，
把原始字节给你，你对比自己的实现。要的话我可以抓。

## 四、关于「Mac 是否完全依赖飞牛插件」

**不是。三条路是并列的，插件只是其中一条。**

~~~
┌─ 路线 A：飞牛插件 API      （今天就能用，但需要 NAS 在线）
│
├─ 路线 B：Mac 自研 cs2 直连  （最理想，不依赖任何东西）
│
└─ 路线 C：EasyNVR HTTP-FLV   （旧方案，依赖 NAS）
~~~

### 各路线对比

| | 路线 A（插件） | 路线 B（自研） | 路线 C（EasyNVR） |
|---|---|---|---|
| 需要 NAS 在线 | ✅ 需要 | ❌ 不需要 | ✅ 需要 |
| 需要插件安装 | ✅ 需要 | ❌ 不需要 | ✅ 需要 |
| 延迟 | 中（多一跳） | **最低** | 中 |
| 开发量 | **零** | 大 | 零 |
| 画质 | 转码后 | **原始** | 转码后 |
| 云台 | ✅ 已实现 | 需自己写 | ❌ |

### 所以回答你的问题

**「如果要用 Mac 应用，是否必须本地局域网有一个插件服务？」**

- 走**路线 A**：是，必须有 NAS + 插件
- 走**路线 B**：不需要，Mac 直连摄像头

**路线 A 的定位**：**快速可用 + 兜底**。
它让你今天就能把 App 跑起来，不用等 cs2 调通。
等路线 B 通了，切换过去即可（这正是你提的「视频源抽象层」的价值）。

### 我的建议

1. **先接路线 A**，把 App 主体跑起来（解码/UI/交互都能验证）
2. **同时排查路线 B 的 UDP 问题**（插网线 + 抓包对比）
3. 抽象层做好，两条路随时切换
