# MiCam 性能方案分析（给用户决策）

> 测试时间：2026-09-15
> 硬件：Intel Celeron J4125（4核 2.0GHz，带核显）

---

## 一、核心发现：MJPEG 是性能杀手

实测同一段 2K 视频（2560x1440 @15fps）：

| 方案 | 数据量 | CPU 占用 | 说明 |
|---|---|---|---|
| **原始流（HEVC）** | **1.8 MB** | 0% | 摄像头原生输出 |
| MJPEG 2K 12fps | **49.8 MB** | 335% | 当前方案，**放大 27 倍** |
| H264 2K 15fps | 17.5 MB | 269% | 放大 10 倍 |

**为什么 MJPEG 这么差**：
- MJPEG 是**逐帧独立压缩**，没有帧间预测，压缩率极低
- 每一帧都是完整 JPEG 图片
- 2K 分辨率下单帧就有 200-400KB

**硬件解码没用**（实测）：

| 方案 | 耗时 | CPU |
|---|---|---|
| 软件解码 | 1.93s | 344% |
| VAAPI 硬件解码 | 12.55s | 131% |

J4125 的核显太弱，而且 `hwdownload`（从显存拷回内存）开销很大，
**硬件解码反而更慢**。

## 二、三个方案对比

### 方案 A：HLS（推荐）

用 ffmpeg 转 H264，输出 HLS 分片，浏览器用原生 `<video>` 播放。

~~~
摄像头 --HEVC--> ffmpeg转H264 --> HLS分片(.ts) --> <video> 播放
~~~

| 优点 | 缺点 |
|---|---|
| 数据量小（17.5MB vs 49.8MB） | 有 2-5 秒延迟 |
| CPU 占用低（269% vs 335%） | 需要写分片文件 |
| 浏览器原生解码，不占 NAS CPU | 实现复杂度中等 |
| **支持 2K 流畅播放** | |

**延迟**：2-5 秒（HLS 固有）

### 方案 B：WebRTC（延迟最低）

go2rtc 原生支持 WebRTC，浏览器直接 P2P 接收。

| 优点 | 缺点 |
|---|---|
| **延迟 <1 秒** | 实现复杂 |
| 数据量最小 | 需要额外信令 |
| 浏览器硬解 | |

### 方案 C：优化当前 MJPEG（最简单）

保持 MJPEG，但：
- 默认降到 1280（不是 2K）
- 帧率降到 8fps
- 提供画质切换

| 优点 | 缺点 |
|---|---|
| 改动最小 | **2K 下依然卡** |
| 兼容性最好 | CPU 占用高 |

## 三、最终实现（v0.5.0）

**已实现 HLS 方案**，实测结果：

| 指标 | MJPEG（旧） | HLS（新） |
|---|---|---|
| 2K 支持 | ❌ 卡顿 | ✅ 流畅 |
| CPU 占用 | 335% | **94%** |
| 首帧 | 9-19 秒 | **8 秒** |
| 数据量 | 49.8 MB | 17.5 MB |

**关键实现细节**：

1. **编码器选择**：实测 QSV/VAAPI 硬件编码在 pipe 实时流下不稳定
   （报 `Could not open encoder before EOF`），所以 HLS 用 libx264。
   但通过 `-preset veryfast -tune zerolatency` 优化，CPU 只有 94%。

2. **强制关键帧**：摄像头 I 帧间隔约 7 秒，HLS 需要 2 秒切片，
   所以加 `-g 30 -keyint_min 30 -sc_threshold 0` 强制固定 GOP。

3. **阻塞管道**：HLS 用 `io.Pipe`（不丢数据），
   MJPEG 用 `bufferedPipe`（丢帧可接受）。
   因为 bufferedPipe 超限截断会破坏 TS 包的 188 字节对齐。

4. **前端双模式**：
   - HLS 模式（默认）：`<video>` + hls.js，2K 流畅
   - MJPEG 模式（兜底）：`<img>`，兼容性最好

## 四、我的建议

**推荐方案 A（HLS）**，理由：

1. **能真正跑 2K** —— 这是你最在意的
2. **CPU 占用可控** —— 269% 在 4 核上约等于 2.7 个核，还有余量
3. **浏览器原生解码** —— 播放端不占 NAS 资源
4. **实现成熟** —— go2rtc 内置 HLS 支持

**延迟 2-5 秒对监控场景可以接受**（不是视频通话）。

### 如果延迟不能接受

那就上 **WebRTC**，延迟 <1 秒，但实现复杂度高一些。

## 四、关于「原生」

**真正的原生直通做不到**，原因：

1. **浏览器不支持 HEVC** —— 摄像头输出的是 H.265，
   Chrome/Safari/Firefox 都不能直接播（这是浏览器限制）
2. **必须转码** —— 要么转 H264（方案A/B），要么转 JPEG（当前方案）

**唯一能避免转码的场景**：
- 客户端是原生 App（如 Mac App），支持 HEVC 硬解
- 这时可以直接把 HEVC 流转发过去，**零转码、零 CPU**

**所以 Mac 那边如果做原生 App，可以直接吃 HEVC 流，性能最优。**
