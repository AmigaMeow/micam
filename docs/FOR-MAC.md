# 给 Mac 客户端的适配说明

> 对应服务端版本 **0.8.1+**
> 如果你在对接 0.3.x ~ 0.7.x，请先看「五、版本差异」

---

## 一、最重要的变化：连接共享

### 1.1 服务端现在支持多客户端同时观看

```
每台摄像头只有一条 cs2 连接（共享）
  +-- consumer A (网页 HLS)
  +-- consumer B (Mac App)
  +-- consumer C (抓拍)
```

**这意味着**：
- 网页和 Mac App 可以**同时看同一台摄像头**，不会互相踢掉
- 抓拍和播放可以**同时进行**
- **不需要**为「连接被占用」做特殊处理了

### 1.2 连接保温

```
最后一个消费者离开后，连接保持 25 秒
  25 秒内再请求 -> 复用连接（0.01 秒出画）
  超过 25 秒    -> 释放连接（下次重新握手约 5 秒）
```

**适配建议**：
- 用户切换设备再切回来（25 秒内）→ 秒开，UI 不用显示 loading
- **不要**为了保持热连接而空转请求，那会一直占着摄像头

## 二、启动耗时预期（重要）

### 2.1 实测数据

| 场景 | 耗时 | 说明 |
|---|---|---|
| HLS 首次（冷连接） | **5.4-6.2s** | 含握手+等关键帧+首分片 |
| HLS 二次（热连接） | **0.01-0.03s** | 复用连接 |
| 抓拍 首次 | 2.4s | |
| 抓拍 热连接 | 1.6s | |
| MJPEG 首帧 | 2.3s | 热连接 |
| 云台操作 | 0.2-0.6s | |
| 设备列表 | 0.3-2s | |

### 2.2 为什么冷启动要 5 秒

```
  CS2 握手            0.3s   协议决定，无法再快
  等摄像头关键帧      2.3s   GOP 决定（摄像头每 1-2s 一个 I 帧）
  ffmpeg 出首个分片   1.0s   hls_time 决定
  ffmpeg 启动/探测    1.5s
                    -----
  合计                5.1s
```

**这是物理下限，不是 bug。**
摄像头不主动给 I 帧，就无法更快解码。

### 2.3 UI 文案建议

```
0.0s  发起请求，显示「连接中」+ 转圈
2.0s  文案改为「正在建立视频流…」
5.0s  开始播放
12s   还没出画 -> 「设备可能被占用」+ 重试按钮
```

**不要在 1-2 秒内判定失败。**

## 三、播放接口建议

### 3.1 优先用 HLS

**为什么**：
1. macOS 的 **CFNetwork 读不了 `multipart/x-mixed-replace`**（你已经踩过），
   HLS 是标准 HTTP 分片，没有这个问题
2. HLS 的 CPU 占用是 MJPEG 的 1/3.5（94% vs 335%）
3. HLS 支持 2K 流畅，MJPEG 在 2K 下会卡

```swift
// HLS 播放列表
GET /api/live/hls?did=<did>&fps=15&w=0

// w=0 表示原画（2K 2560）
// 也可以传 1280 / 640 降低带宽
```

### 3.2 m3u8 分片路径（注意！）

m3u8 里的分片行是**相对路径**，且**保留了 `hls` 段**：

```
#EXTINF:1.000000,
hls?did=1000000102&seg=seg0.ts
```

**交给播放器按标准相对路径解析即可**：

```
base:  http://nas/app/micam/api/live/hls?did=X
相对:  hls?did=X&seg=seg0.ts
结果:  http://nas/app/micam/api/live/hls?did=X&seg=seg0.ts   ✅
```

**不要手工拼接**成 `.../api/live/seg?...` —— 那是错的（会 404）。

### 3.3 MJPEG（兜底用）

```
GET /api/live/mjpeg?did=<did>&fps=12&w=1280
Content-Type: multipart/x-mixed-replace; boundary=mjpegframe

每帧：
  --mjpegframe\r\n
  Content-Type: image/jpeg\r\n
  Content-Length: N\r\n
  \r\n
  <N 字节 JPEG>\r\n
```

**每帧都带准确的 Content-Length**，可以按长度切，
也可以按 `FFD8FF` / `FFD9` 标记切。

## 四、错误处理

### 4.1 状态码

| 码 | 含义 | 客户端动作 |
|---|---|---|
| 200 | 成功 | - |
| 400 | 参数错误 | 检查 did |
| 404 | 设备不存在 | 刷新设备列表 |
| 504 | 播放列表未就绪 | **2 秒后重试，最多 3 次** |
| 502 | 上游失败 | 看 msg |
| 503 | 设备离线 | **不要重试**，提示用户 |

### 4.2 常见错误消息

```
设备离线（<name>），无法播放
  -> 不要重试

miss: auth: {"result":"failed","code":3}
  -> 凭据失效，服务端会自动刷新。3-5 秒后重试

throttle deny
  -> 小米云限流，等 30 分钟

播放列表尚未生成，请稍候重试
  -> HLS 转码启动中，重试即可
```

### 4.3 重试策略

```swift
// 建议
504          -> 重试（2s, 4s, 8s），3 次后提示
auth failed  -> 等 3-5 秒重试一次
设备离线     -> 不重试
```

## 五、版本差异（0.3.x → 0.8.1）

| 项 | 0.3.x（你上次对接的） | 0.8.1（现在） |
|---|---|---|
| **并发云台崩溃** | 会崩进程 | **已修复** |
| **开流后云台 33-77 秒** | 33-77s | **0.2-0.6s** |
| **多客户端同时观看** | 互斥（等 60 秒） | **共享，不互斥** |
| **HLS 起播** | 无 HLS | **5.4s 冷 / 0.01s 热** |
| **MJPEG 首帧** | 9s | **2.3s** |
| **抓拍** | 6.7s | **2.4s / 1.6s 热** |
| **CW500 间歇 0 字节** | 有 | **已修复（凭据刷新）** |
| m3u8 分片路径 | - | `hls?...`（相对，保留 hls 段） |
| boundary | `mjpegframe` | 同 |

### 5.1 你之前报的三个问题现状

**① 并发云台导致进程崩溃** → 已修复（云台独立锁）

**② 开流后首次云台 28-77 秒** → 已修复
```
实测：无流时 0.19s，开流后 0.25s
原因：v0.5.0 把云台改成独立连接，不再和视频共用锁
```

**③ CW500 MJPEG 间歇 0 字节** → 已修复
```
根因：cs2 凭据过期（实测 8 小时），旧代码无条件信任缓存
修复：凭据失效自动刷新，且刷新失败时保留旧凭据
      （避免小米云限流时彻底不可用）
```

## 六、你应该做什么

### 6.1 必做

1. **切到 HLS 为主**（避开 CFNetwork 的 multipart 问题）
2. **冷启动给 5-6 秒预期**，UI 不要 1-2 秒就判失败
3. **504 重试**（2s/4s/8s）
4. **云台串行化**（你已经做了）
5. **启动时调 `/api/dev/capabilities`** 探测能力

### 6.2 建议

6. **利用连接保温**：25 秒内切回同一设备直接显示（不用 loading）
7. **不要并发发多个播放请求**（虽然支持共享，但没必要）
8. **设备离线不要重试**

### 6.3 可以删掉的代码

旧版本可能需要这些 workaround，现在不需要了：

- 云台请求前的「等工作流让出连接」逻辑
- 「连接被占用」的检测和提示
- MJPEG 读取失败后长时间重试

## 七、快速自测

```bash
# 1. 服务在吗
curl http://<nas>:8900/api/health

# 2. 能力探测
curl http://<nas>:8900/api/dev/capabilities | python3 -m json.tool

# 3. 设备列表
curl http://<nas>:8900/api/devices

# 4. HLS 播放列表（首次约 5 秒）
time curl 'http://<nas>:8900/api/live/hls?did=<did>&fps=15&w=0'

# 5. 再来一次（应该 0.01 秒）
time curl 'http://<nas>:8900/api/live/hls?did=<did>&fps=15&w=0'

# 6. 抓拍
curl -o snap.jpg 'http://<nas>:8900/api/live/snapshot?did=<did>&w=0'

# 7. 云台
curl -X POST http://<nas>:8900/api/ptz/move \
  -H 'Content-Type: application/json' \
  -d '{"did":"<did>","operation":3}'
```
